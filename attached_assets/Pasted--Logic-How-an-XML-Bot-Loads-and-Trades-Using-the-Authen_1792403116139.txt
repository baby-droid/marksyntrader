# Logic: How an XML Bot Loads and Trades Using the Authenticated Deriv Account

For your MarkSynTrader app, the XML bot should execute through a single authenticated Deriv WebSocket session. The account selected and authorized by the user must be the account used for proposals, purchases, balance updates and contract monitoring.

The core principle is: load the XML strategy, connect it to the authenticated account, execute its original trading logic, and route every trade through the same account-aware execution engine.

## 1. Complete execution flow

1\. Load XML bot

Import XML → validate blocks → generate JavaScript

2\. Resolve authenticated account

Verify authorization and identify the selected account

3\. Bind bot to account session

Attach runtime, WebSocket request router and account-specific state

4\. Start market subscriptions

Receive live ticks and evaluate the XML bot's original conditions

5\. Validate and purchase

Check account, balance, stake, contract parameters and risk rules before buying

6\. Monitor and reconcile

Track contract outcome, balance, profit/loss and bot status

## 2. Authenticate the account before starting the bot

The bot must never choose an account merely from a stored label such as “Real” or “Demo.” It must verify which account the WebSocket session is actually authorized to use.

Deriv's documented workflow uses an authorization request before authenticated trading operations.&#x20;

The required logic is:

1. User logs in through the existing Deriv OAuth or authorized-token flow.
2. The app retrieves the user's available accounts through its existing authentication mechanism.
3. User selects a specific account.
4. The app authorizes the appropriate WebSocket session for that account.
5. The app verifies the authorization response, account login ID, currency, account type and required permissions.
6. The app obtains the current balance.
7. Only then does it enable the bot's trading controls.

```
async function prepareBotForTrading(bot, accountSession) {
  if (!accountSession?.isAuthenticated) {
    throw new Error("Authenticate your Deriv account first");
  }

  if (accountSession.loginId !== accountSession.authorizedLoginId) {
    throw new Error("Selected account does not match authorized session");
  }

  if (!accountSession.hasTradePermission) {
    throw new Error("Trading permission is required");
  }

  if (!bot.isValid || !bot.strategy) {
    throw new Error("Bot configuration is invalid");
  }

  const balance = await accountSession.getVerifiedBalance();

  if (!balance || balance.loginid !== accountSession.loginId) {
    throw new Error("Account balance verification failed");
  }

  bot.accountId = accountSession.loginId;
  bot.currency = balance.currency;
  bot.status = "READY";

  return { ready: true, accountId: bot.accountId };
}
```

This is reference logic. `accountSession` and its methods must be connected to your app's actual authentication implementation.

Security rule: Never expose a user's password or long-lived API token in XML, generated bot JavaScript, logs, or shared bot configuration. Use the existing secure authentication flow and appropriate token permissions.

## 3. How the XML bot should generate and execute trades

Once the account is verified, the XML bot follows this lifecycle:

| Stage               | Action                                                                          |
| ------------------- | ------------------------------------------------------------------------------- |
| XML import          | Parse and validate the bot's blocks                                             |
| Code generation     | Generate JavaScript using the existing Blockly generator                        |
| Runtime binding     | Connect the generated strategy to the selected account session                  |
| Market subscription | Receive ticks for the bot's configured symbol                                   |
| Entry evaluation    | Execute the bot's original entry conditions                                     |
| Risk validation     | Check stake, balance, loss limits and existing positions                        |
| Proposal            | Request a quote for the exact contract                                          |
| Purchase            | Submit a buy request using the valid proposal ID                                |
| Confirmation        | Record the returned contract ID and purchase details                            |
| Monitoring          | Subscribe to contract updates and process settlement                            |
| Next trade          | Resume the bot's loop only according to its original strategy and risk settings |

The Deriv API documents the `proposal`, `buy` and `proposal_open_contract` operations for this trading workflow.&#x20;

## 4. Example: account-aware trade execution

This example demonstrates the control flow your developer should implement. It assumes your existing WebSocket client already has a request-response manager and an authenticated account session.

```
async function executeBotTrade(bot, signal, account) {
  // 1. Confirm the account is still authorized.
  await account.assertAuthorized();

  // 2. Confirm that the signal belongs to this bot.
  if (!bot.strategy.validateSignal(signal)) return;

  // 3. Check account and bot risk controls.
  const risk = await bot.riskManager.validate({
    accountId: account.loginId,
    stake: bot.settings.stake,
    signal
  });

  if (!risk.approved) return;

  // 4. Request a proposal using the bot's actual settings.
  const proposal = await account.requestProposal({
    symbol: bot.settings.symbol,
    contractType: signal.contractType,
    duration: bot.settings.duration,
    stake: bot.settings.stake,
    barrier: signal.barrier,
    currency: account.currency
  });

  // 5. Verify the returned quote before buying.
  if (!proposal?.id || !proposalMatchesBot(proposal, bot, signal)) {
    throw new Error("Proposal validation failed");
  }

  // 6. Recheck risk immediately before the purchase.
  await account.assertAuthorized();

  const finalRisk = await bot.riskManager.validate({
    accountId: account.loginId,
    stake: bot.settings.stake,
    signal
  });

  if (!finalRisk.approved) return;

  // 7. Purchase through the same authorized session.
  const result = await account.buy({
    proposalId: proposal.id,
    maximumPrice: proposal.askPrice
  });

  if (!result?.contractId) {
    throw new Error("Purchase was not confirmed");
  }

  // 8. Record and monitor the actual purchased contract.
  await bot.tradeJournal.record({
    accountId: account.loginId,
    contractId: result.contractId,
    botId: bot.id,
    signalId: signal.id
  });

  await account.monitorContract(result.contractId);
}
```

The methods shown are placeholders for your existing API client, not literal Deriv SDK method names. Map the parameters to the actual response schemas and preserve the bot's original contract configuration. In particular, validate the currency, contract type, barrier, duration, quote and maximum purchase price against the returned proposal.

## 5. What happens if the user changes accounts?

Account switching must be handled explicitly.

- Pause new purchases from the old account session.
- Continue monitoring contracts already purchased on that account.
- Establish or select a session authorized for the new account.
- Verify its login ID, account type, currency, permissions and balance.
- Rebind eligible bots only after validation.
- Never submit a pending trade intended for the old account through the new account's session.
- Keep trade history and profit/loss separated by account.

If a buy request times out, the app must reconcile its outcome before retrying. Otherwise, an apparently failed purchase could actually have succeeded.
