## Prompt: Fast Mode Optimization (High-Speed Contract Execution)

Implement a new execution mode named **Fast** that is specifically designed to minimize internal processing latency between receiving a market tick and submitting a valid contract purchase request. The objective is not to bypass exchange, broker, or network latency, but to optimize the application's own execution pipeline so that, once a trading condition is satisfied, the purchase request is dispatched as quickly as possible using the latest available tick.

When the user enables **Fast** mode, the system should automatically prioritize execution speed over visual effects and non-essential background work. Keep a single persistent WebSocket connection open throughout the session to avoid reconnection overhead. Subscribe to all required market streams only once and continuously process incoming tick, proposal, balance, transaction, and open-contract updates through the same connection. Never reconnect unless the connection is genuinely lost.

Build the execution engine using an event-driven architecture. Every incoming tick should immediately trigger the strategy evaluation process without polling, artificial delays, or fixed-interval timers. As soon as a new tick arrives, update the internal market state, evaluate the trading conditions, and, if all configured rules are satisfied, generate and submit the purchase request immediately. The strategy evaluation should always use the newest confirmed market tick available at the time of execution.

Separate the trading engine from the user interface. Trading logic must execute independently of chart rendering, animations, transaction tables, and other visual updates. UI rendering should never delay strategy evaluation or contract submission. Background tasks such as logging, journaling, statistics, analytics, and historical storage should execute asynchronously after the purchase request has been sent so they cannot block the execution pipeline.

Implement a lightweight in-memory state store that keeps only the latest market values required by the strategy. Avoid repeatedly querying historical arrays or recalculating unchanged indicators. Cache reusable computations and invalidate them only when new market data requires an update. Use efficient data structures to minimize memory allocation and garbage collection during high-frequency execution.

The purchase engine should maintain prevalidated contract parameters whenever possible. Stake, duration, symbol, contract type, currency, and user-selected settings should already be prepared before the next trading opportunity occurs. Once a signal is confirmed, only the final purchase request should need to be constructed and transmitted.

Avoid unnecessary waiting mechanisms such as sleep calls, debounce timers, repeated retries before submission, or blocking loops. Process market messages sequentially while allowing UI updates and logging to execute independently. If multiple ticks arrive rapidly, maintain a lightweight queue that always processes events in order while ensuring the latest market state is available to the strategy.

Optimize rendering performance by batching interface updates using animation frames instead of triggering a full interface redraw for every incoming tick. Only refresh components that have actually changed, such as the current tick, balance, active contract status, and latest transaction row. Charts should receive incremental updates rather than being fully regenerated.

The **Fast** mode should clearly display its active status in the interface so users understand that the application is prioritizing execution responsiveness. Visual effects should be reduced where appropriate to preserve CPU resources for the trading engine. Any expensive calculations unrelated to contract execution should be deferred until after the purchase request has been submitted.

Provide automatic error handling for temporary network interruptions without interrupting the execution engine. If the WebSocket disconnects, reconnect immediately, restore subscriptions automatically, synchronize internal state, and continue listening for new ticks. Failed purchase requests should be logged with detailed diagnostic information, but the logging process must not block the processing of future market events.

Instrument the system with performance metrics that measure internal execution time, including the interval between tick reception and strategy evaluation, strategy evaluation and purchase request creation, purchase request creation and transmission, and overall internal processing latency. These metrics should be displayed in a developer diagnostics panel to help identify bottlenecks during testing and optimization.

The overall design goal is to produce a highly responsive trading engine that minimizes software-induced latency while remaining reliable, deterministic, and compliant with the broker's normal API behavior. The **Fast** mode should always use the most recent confirmed market data, execute immediately after a valid signal is detected, and maintain consistent performance under sustained high-frequency tick streams without sacrificing application stability.
