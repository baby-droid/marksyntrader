# FAST Engine — Tick-by-Tick Execution for All XML Bots

For your MarkSynTrader app, the FAST button should act as a global acceleration layer for every XML bot loaded into the app, not just the bot currently selected.

When FAST is enabled, the engine should process every incoming Deriv tick immediately, evaluate the active bot's strategy, and execute eligible trades as soon as the required contract and risk checks permit.

There is one important technical distinction: you can make analysis and dispatch much faster, but you cannot guarantee a completed trade on every tick or eliminate Deriv's network and contract-processing latency. FAST must not bypass the bot's entry rules or the broker's required responses.

## 1. How the global FAST engine should work

FAST — GLOBAL ENGINE

One switch controls all compatible XML bots

1\. XML Bot Registry

Discover every loaded bot, preserve its strategy, contract type, barrier, duration, stake and variables.

2\. Shared Tick Router

Distribute each relevant tick to the active bots without duplicate subscriptions or repeated setup work.

3\. Parallel Analysis

Evaluate independent bot strategies concurrently, maintaining separate state for each bot.

4\. Execution Coordinator

Validate signals, prevent duplicate buys, manage concurrency and submit eligible trades.

5\. Trade Monitor

Track confirmations, settlements, errors, profit/loss and bot-specific status.

## 2. The critical rule: accelerate every loaded XML bot

The app must not simply change a global speed variable and assume that all bots are faster. It must connect the FAST engine to the actual execution path of each imported XML bot.

Implement these rules:

- Preserve XML logic: Do not overwrite the bot's contract type, barriers, duration, stake calculations, martingale rules or entry conditions.
- Optimize execution: Remove unnecessary waits, repeated initialization, redundant tick-history requests and duplicate event listeners where safe.
- Shared market data: Let compatible bots consume a common tick stream for each market.
- Independent bot state: Each bot must maintain its own variables, counters, signals and trade history.
- Central execution control: Prevent conflicting bots from exceeding the account's configured concurrency and risk limits.
- Compatibility handling: Bots with unsupported blocks, custom JavaScript or incompatible execution loops must be identified instead of silently modified.

## 3. XML bot acceleration logic

Use an adapter to connect each imported bot to the shared engine.

```
async function enableGlobalFastMode() {
  fastEngine.enabled = true;

  for (const bot of loadedXmlBots) {
    if (!bot.isValid || bot.isStopped) continue;

    const adapter = getCompatibleExecutionAdapter(bot);

    if (!adapter) {
      reportBotStatus(bot.id, "Unsupported FAST adapter");
      continue;
    }

    adapter.preserveStrategy();
    adapter.enableIncrementalTickProcessing();
    adapter.attachSharedMarketFeed();
    adapter.enableAsyncExecution();

    reportBotStatus(bot.id, "FAST enabled");
  }

  startSharedTickRouter();
}
```

This is reference logic, not a drop-in implementation. Your app must supply the registry, adapter and execution methods.

For Blockly-generated XML, inspect the actual block definitions and generated JavaScript before attempting to accelerate execution. Some blocks contain asynchronous waits or stateful loops that cannot safely be removed.

## 4. How to reduce the delay between a tick and a trade

Deriv supports live tick subscriptions, proposal requests and contract purchases through its API. The tick stream can notify your app as new prices arrive, while a purchase uses a proposal ID or supported contract parameters.&#x20;

The execution pipeline should therefore:

1. Maintain a persistent, healthy WebSocket connection.
2. Process the incoming tick immediately.
3. Evaluate the bot's strategy without reloading its XML.
4. Reuse a current proposal subscription where appropriate, while checking that the quote and contract parameters remain valid.
5. Send the buy request as soon as a valid signal and required checks are satisfied.
6. Match every response to its originating bot and request.
7. Reconcile timeouts and errors before retrying.

Do not use artificial zero-delay loops or send unlimited buy requests. They cannot make network responses instantaneous and can overwhelm your app or create unintended trades.

## 5. Define what the FAST button guarantees

| Behavior         | Expected result                                                   |
| ---------------- | ----------------------------------------------------------------- |
| Tick processing  | Every received, valid tick is evaluated                           |
| Bot acceleration | Every compatible loaded bot uses the optimized execution path     |
| Entry execution  | Immediate dispatch after strategy and risk checks pass            |
| Trade frequency  | Limited by valid signals, execution capacity and broker responses |
| XML strategy     | Preserved                                                         |
| Network latency  | Reduced where possible, never guaranteed to be zero               |
| Risk controls    | Always active                                                     |
